# \## 6. Варіант № 4 — DuckDB замість pandas

# 

# У `bench/variant.py` обробку даних реалізовано одним SQL-запитом DuckDB.

# 

# Для трьох CSV-файлів використано `read\_csv\_auto`, оператор `SELECT DISTINCT` для вилучення повторних погодинних записів, фільтрацію за містом і допустимим діапазоном PM2.5, групування за містом і днем із `HAVING count(\*) >= 18` та річне агрегування. Результат перетворюється у pandas DataFrame методом `.df()`.

# 

# Команда `python measure.py verify` підтвердила еквівалентність результатів усіх реалізацій.

# 

# \### Порівняння DuckDB з optimized pandas

# 

# | Середовище | pandas, Дж/R | DuckDB, Дж/R | pandas, с/R | DuckDB, с/R |

# |---|---:|---:|---:|---:|

# | Local · CodeCarbon | 1,154 | 5,083 | 0,0438 | 0,1292 |

# | CI · CodeCarbon | 0,291 | 1,097 | 0,0246 | 0,0721 |

# | CI · Eco CI | 0,103 | 0,430 | 0,0253 | 0,0741 |

# 

# Локально optimized pandas споживає приблизно у 4,4 раза менше енергії та виконується у 2,95 раза швидше за DuckDB.

# 

# У GitHub Actions optimized pandas також продемонстрував кращі результати.

# 

# Водночас DuckDB є значно ефективнішим за baseline:

# 

# \- локально: економія енергії 88,9 %, прискорення 13,7 раза;

# \- CI CodeCarbon: економія 91,7 %, прискорення 16,0 раза;

# \- CI Eco CI: економія 91,1 %, прискорення 15,9 раза.

# 

# \### Відповідь на творче питання

# 

# Вбудований SQL-рушій DuckDB доцільний для великих аналітичних наборів міських даних, коли необхідно виконувати фільтрацію, JOIN, групування та агрегування без попереднього завантаження всього набору в DataFrame.

# 

# Особливо це стосується задач OLAP: аналізу історичних даних, телеметрії, показників за великими часовими інтервалами та побудови аналітичних зрізів.

# 

# Для невеликих наборів даних і тісної інтеграції з Python зручнішою може бути бібліотека DataFrame. У проведеному експерименті optimized pandas продемонстрував менше енергоспоживання та швидше виконання в усіх досліджених середовищах.

# 

# Накладні витрати запуску SQL-рушія для невеликого набору можуть перевищувати переваги оптимізатора DuckDB.

# 

# DuckDB орієнтований переважно на аналітичне навантаження OLAP, тоді як для OLTP характерні часті короткі транзакції, точкові вставки та оновлення. Вибір технології залежить від характеру навантаження, обсягу даних і способу їх обробки.

# 

# 4\. Реалізація DuckDB в усіх досліджених середовищах виявилася ефективнішою за baseline, але поступилася optimized pandas.

# 

# 5\. SCI локальної optimized-версії становив 0,1577 мг CO₂e/R, а baseline — 6,2911 мг CO₂e/R.

# 

# 6\. Сумарний SCI виміряних етапів основного CI-конвеєра становить 0,031483 г CO₂e за один запуск. За сценарію 22 000 запусків на рік прогнозований вуглецевий слід становить 0,693 кг CO₂e.

# 

# \### Обмеження

# 

# \- Локально CPU вимірювався через windows\_emi, а енергоспоживання RAM оцінювалося за моделлю CodeCarbon.

# \- GitHub Actions використовує модельні оцінки енергоспоживання замість прямого апаратного вимірювання.

# \- Параметри GitHub-раннерів можуть відрізнятися між запусками. Під час повторного експерименту CodeCarbon використовував TDP 16 Вт замість попередніх 280 Вт.

# \- Фактичний географічний регіон GitHub-раннера невідомий, тому використано фіксовану вуглецеву інтенсивність.

# \- Для України використано значення інтенсивності електромережі за 2022 рік — 250,47 г CO₂e/кВт·год.

# \- PCF використано для сімейства ноутбуків Victus by HP 15-fb.

# \- Локальні вимірювання виконано за 5 повторами, CI CodeCarbon — за 3 повторами. Для одиничних оцінок Eco CI довірчий інтервал не розраховується.

# \- Річна оцінка базується на одному успішному запуску та не враховує варіативність тривалості майбутніх запусків і невиміряні етапи роботи раннерів.
